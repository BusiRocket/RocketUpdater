### P1 — The proposed unattended sudoers policy is unreachable through the current runner

**Audit claim (§6):** the NOPASSWD drop-in replaces the interactive `sudo -v` timestamp for launchd.

**Evidence:** `RocketUpdater.sh:40` grants `SUDO_AVAILABLE=true` only when `sudo -n true` succeeds; `plugins/osx.sh:55` repeats the same `sudo -n true` probe. The proposed sudoers file does not authorize `/usr/bin/true`, only exact `softwareupdate`, `purge`, `periodic`, and `dscacheutil` invocations. Under launchd, the probe therefore remains false and the allowed commands are never attempted.

Proof command:

```sh
awk 'NR>=35 && NR<=50 {print NR ":" $0}' RocketUpdater.sh
awk 'NR>=52 && NR<=59 {print NR ":" $0}' plugins/osx.sh
sed -n '/Cmnd_Alias ROCKET_SWUPDATE/,/Defaults!ROCKET_MAINT/p' AUDIT-2026-08-31.md
```

Correction: do not use a generic `sudo -n true` capability bit for the scheduled path. Invoke only each allowlisted absolute command with `sudo -n`, capture its status, and keep interactive `sudo -v`/keepalive separate.

### P1 — The proposed single-instance lock cannot run on this machine

**Audit claim (§6):** use `/opt/homebrew/bin/flock -n 9`.

**Evidence:** neither `flock` nor `/opt/homebrew/bin/flock` exists. The lock command would fail after opening the lock file; with `set -e`, scheduling would abort instead of preventing overlap.

Proof command:

```sh

```

Correction: use macOS's native `/usr/bin/lockf -s -t 0 -k <lock> <command>`. Its installed manual explicitly provides fail-fast execution while holding a BSD lock; no new dependency or stale-PID protocol is needed.

### D1 — Concede the criterion; hold on class-by-name deletion

**Verdict:** concede that reconstructability, not the mere fact of deletion, is
the useful boundary. Hold against treating `cleanup`, `cache`, or `prune` as
proof that a target satisfies that boundary. The plan now uses an explicit
scheduled-deletion allowlist whose preconditions are tested per target.

**Evidence:** today's Homebrew dry run would reclaim only 51.9 MiB, all under
the Homebrew cache, temporary Cellar, or Python bytecode paths. It can therefore
run only after its immediately preceding dry run proves every candidate is in
the approved cache/temp roots. The current Docker plugin is not one cleanup:
it removes stopped containers, all unused images, volumes, networks, and build
cache. Volumes and locally built images are not inferably reconstructable from
a public registry. Moreover, OrbStack is stopped today, so the provenance of
the build cache cannot even be inspected. Only an independently proven cache
class may be allowed; the broad Docker sequence remains rejected. The npm cache
currently has 284 indexed request authorities and every one is
`registry.npmjs.org`, so it meets the public-registry condition today. Its guard
must re-prove that fact on every run and reject private, credential-bearing, or
unparseable authorities.

### D4 — Hold: macOS newsyslog cannot copy-truncate this open descriptor

triggering rotation must close its logs and reopen them afterward. The OpenClaw
job is currently in `spawn scheduled`, has run 125,661 times, last exited 1,
and inode 1,040,785,639 grew from 3,326,942,172 to 3,326,969,017 bytes during
inspection. This is a crash loop and logging defect, not only a retention issue.

### Could RocketUpdater have broken the global OpenClaw package?

**Verdict:** `npm.sh` is a plausible mechanism, but attribution is unproven.
`npx.sh` is not a plausible mechanism for deleting the global tree. A Homebrew
Node upgrade is an adjacent runtime change, not evidence of the deletion.

`plugins/npm.sh:23-55` runs `npm install -g npm@latest`, obtains global updates
with `ncu -g`, and runs `npm install -g "${pkg_name}@${new_version}"` for each
parsed item. That command replaces the selected global package tree. If
OpenClaw appeared in `ncu -g`, a failed or interrupted global install could
leave it incomplete. The same plugin's `npm cache clean --force` operates on
npm's cache, not `/opt/homebrew/lib/node_modules`.

`plugins/npx.sh:17-19` only runs `npx -y clear-npx-cache`; its measured target is
`$HOME/.npm/_npx`, not the global prefix. It cannot explain absent files under
`/opt/homebrew/lib/node_modules/openclaw`.

Homebrew's installed Node formula owns npm under
`/opt/homebrew/Cellar/node/26.8.1/libexec/lib/node_modules/npm`, while
`npm root -g` is `/opt/homebrew/lib/node_modules`. A Homebrew Node upgrade can
change Node/npm behavior and therefore is worth bracketing, but the observed
layout does not prove that Homebrew removed the third-party OpenClaw tree.
Targeted npm-debug-log and shell-history searches found no OpenClaw uninstall,
remove, or update command. No RocketUpdater LaunchAgent or cron schedule exists;
shell history does show manual RocketUpdater executions, so absence of a
scheduler does not exonerate the npm plugin.

An additional trap is that `npm ls -g --depth=0 --json` exits 0 and exposes no
top-level `problems`, yet reports OpenClaw with `version: null`; the directory
has neither package.json nor `dist/index.js`. Therefore the plan adds
`snapshot_global_npm_packages`, which enumerates actual package directories,
hashes package.json, validates declared bins/entrypoints, and compares snapshots
before/after every global npm update and any Homebrew Node upgrade. Unexpected
disappearance or a broken selected package fails the run and stops subsequent
global upgrades; it does not silently reinstall or delete residue.
